## 검토했지만 결함으로 단정하지 않은 항목

- standalone 성유물 검수 화면의 `자동인식을 켜면…` 문구는 스위치가 켜진 모습과 어긋나지만, 실제 앱의 `EnsureRelicPage`는 감지 상태를 따로 넣는다. 해당 PNG만 보고 실제 앱 결함으로 세지 않았다.
- 전후 비교에서 옵션이 다른 행의 빈 칸은 같은 속성을 나란히 비교하기 위한 정상 동작이다. 비어 있는 행을 줄여 서로 다른 옵션을 같은 줄로 맞추지 않는다.
- 일정의 자료 예상 표시는 실시간 값과 구분하는 정보다. 대시보드를 단순하게 보이게 하려고 숨기지 않는다.
- 긴 오버레이의 아래쪽 일부가 viewport 밖에 있는 것은 현재 전광판 스크롤의 의도된 상태다. 정지 PNG 한 장으로 데이터 누락으로 판단하지 않는다.

## 리벤 적용·불러오기 명령의 활성 조건

독립 검토에서 근접의 `현재 근접 모딩에 가정 적용`이 옵션·수치가 비어 있어도 primary로 활성화되는 문제를 발견했다. 부모 담당자의 추가 지시에 따라 이 항목도 이번 수정에 포함했다.

- 근접은 기존 범위 검증을 통과한 옵션만 적용 후보로 유지한다. 표시 코스트·극성·목적 슬롯이 유효하고 미채택 순환 결과가 없을 때 적용 버튼을 활성화한다. 옵션·수치·장착 정보를 지우면 즉시 비활성화하며 복구하면 다시 활성화한다. 기존 검증 결과를 재사용하고 별도 DPS 계산을 추가하지 않는다.
- 주무기·보조무기의 적용 버튼에는 이미 동일한 유효성 게이트가 있었다. 이 규칙을 바꾸지 않고 비활성 이유와 미채택 순환 상태의 tooltip을 보강했다.
- 근접과 총기의 장착 리벤 가져오기는 실제 모딩 슬롯에 리벤이 있을 때만 활성화한다. 슬롯에서 뺐지만 편집·복원을 위해 남겨 둔 메타데이터만으로 장착 상태로 판단하지 않는다. 공통 배율의 근접 리벤을 과거 WeaponId 자체 때문에 차단하지 않는다.
- 비활성 버튼도 hover로 사유를 확인할 수 있다. 옵션 범위·가정 적용·DPS/TTK 계산식은 변경하지 않는다.

`RivenActionChecks`는 실제 UI Automation Invoke로 비활성 적용 차단, 옵션·수치·코스트·극성의 변경과 복구, 적용 후 슬롯 장착, 실제 장착 리벤 불러오기와 슬롯 해제 후 비활성을 확인한다. 소총·산탄총·권총은 Braton·Strun·Lato 자료의 기존 범위 안 수치를 사용한다. 해당 검사는 `--riven-smoke`의 작업실 UX 검사에 연결했으며 통합 실행 결과를 별도로 기록한다.

## 검수

코드 반영 후 통합 Release 빌드와 격리 UI 검수에서 다음을 확인한다. 검수 실행 전에는 통과로 표시하지 않는다.

- `--inventory-check`: 실제 가져오기 버튼의 실패 처리, 의미 색, 정상 복구, 부분 응답 구분, 직접 획득 장비의 상세 문구와 비용 표시.
- `--riven-capture-check`: UI Automation으로 실제 클립보드 읽기/수동 취소 버튼을 누르고 토큰 취소, 시작 버튼 복구, 자동 인식 스위치 유지 확인. 검수용 이미지 공급과 판독 대기 seam을 사용하며 실제 클립보드는 읽지 않는다.
- `--riven-smoke`: 근접·소총·산탄총·권총의 실제 적용·장착 리벤 가져오기 명령과 유효성 상태 전환.
- `--smoke`: 최소 크기·배율·글꼴·팝업의 전체 회귀 렌더.

최종 산출물의 PNG와 종료 코드·검사 수는 통합 검수 결과에 기록한다. 실제 모니터 이동·HDR·독점 전체화면·실제 계정 동기화 성공률을 이 격리 UI 검수의 통과 범위에 포함하지 않는다.

## 인벤토리 자동 확인의 OCR 우선 양보

별도 성능 리뷰의 `InventoryMemoryReader` 자동 slice API와 화면을 연결했다. 기존 30초 자동 확인·2분 시세 갱신 간격은 유지한다. 자동 요청이 일부 영역만 확인했거나 OCR이 진행 중이면 단일 3초 DispatcherTimer로 다음 확인을 예약한다. 매번 timer를 정지한 뒤 한 번만 실행하고 필요할 때 다시 예약하므로 대기 Task나 즉시 반복 루프가 쌓이지 않는다.

워커에서 읽는 `CanReadGame`은 부모 담당자가 연결한 원자적 `OcrActivity.IsBusy` 상태를 사용한다. WPF 요소를 워커에서 조회하지 않는다. 목록 확인 성공·전체 영역 종료·자동 동기화 끄기·페이지 Dispose에서 이어읽기를 중단한다. 명시적인 수동 요청은 기존 수동 예산을 사용하고 자동 반복을 새로 만들지 않는다. 마지막 정상 목록 보존과 부분 응답의 업데이트 차단은 유지한다.

`InventoryContinuationChecks`는 실제 timer의 양보/재개·중단을 stub 응답으로 검수하며 게임 메모리를 읽지 않는다. 별도 성능 담당자의 `InventoryMemoryChecks`는 자기 검수 프로세스 안의 가짜 3MiB 영역에서 청크 경계 JSON의 이어읽기와 수명을 검증한다. 이 검수도 실제 게임·다른 프로세스·계정 데이터에 접근하지 않는다.

## 처음 사용하는 사람의 작업 흐름 재검토

추가 지시에 따라 '컨트롤이 작동하는가'와 '처음 화면에서 다음 행동을 찾을 수 있는가'를 분리했다. 다음은 상용 프로그램의 문법을 참고한 판단이며, 실제 신규 사용자 모집·관찰 조사를 수행했다는 의미는 아니다.

공식 참고 자료는 [Microsoft Command bar](https://learn.microsoft.com/en-us/windows/apps/design/controls/command-bar), [Fluent 2 Toolbar](https://fluent2.microsoft.design/components/web/react/core/toolbar/usage), [Fluent 2 Switch](https://fluent2.microsoft.design/components/web/react/core/switch/usage), [VS Code 사용자 인터페이스](https://code.visualstudio.com/docs/editing/getting-started/userinterface)다. 자주 쓰는 현재 작업은 전면에 두고 보조 명령은 표준 메뉴에 모으는 명령 위계, 즉시 적용되는 스위치, 관련 설정을 해당 상태 옆에서 찾는 배치, 선택한 대상을 명시적으로 실행하는 분리를 적용했다. WPF 앱을 WinUI/웹으로 옮기거나 다른 프로그램의 화면 전체를 복제하지 않는다.

메뉴는 native ContextMenu/MenuItem으로 방향키·Enter 실행·Escape/바깥클릭 닫기·초점 복귀를 사용한다. 검색 후보는 현재의 명시적 화살표 선택과 Enter 확정 규칙을 보존한다. 가격·수율·조건·법적 출처 정보와 기존 설정은 삭제하지 않는다. 새 상시 타이머, 무한 애니메이션, 반복 OCR은 추가하지 않는다.

추가 검증은 `RelicCommandChecks`(메뉴와 설정의 실제 UIA·키보드 동작), `--relic-check`(확정/미확정 보상·수정·시세), `--relic-workflow-check`(저장한 실제 스크린샷), `--ux-review-check`(최소 크기·배율·직접선택/취소)에서 진행한다. 신규 PNG의 시각 확인과 이 행동 검사 결과가 나오기 전까지 확장 UX 검수 완료로 표시하지 않는다.

## RC3 통합 이미지의 재검토와 후속 마감

`artifacts/ocr-performance-20261027/validation/equipment-navigation`의 전체요약·크레딧·거래 목록·리벤 상태·성유물 상태를 1280/1760, 어두운/밝은 테마에서 실제 이미지로 열었다. `validation/inventory`의 초기 미연동·제작 계획·완료 장비 1.5배 이미지도 확인했다. 상태바의 스위치/설정, 리벤 빈 상태의 입력 시작과 비활성 적용, 추천 목록과 상세의 분리는 시각적으로 확인했다. 이 확인만으로 새 사용자 시험을 통과했다고 표현하지 않는다.

두 가지 후속 결함/불필요한 경쟁을 발견하고 담당자에게 먼저 공유한 뒤 수정했다.

- 성유물 빈 화면에서 기본 대기 Status가 상단 상태바와 중복되고 가격 주의·출처·개인정보·최소 해상도 문단이 핵심 행동과 같은 층위로 노출됐다. 정확히 기본 대기 문자열만 접고 다른 진행·완료·오류 상태는 유지한다. 기존 참고 문구는 '시세·인식 기준' Expander로 모아 모두 보존했다.
- 완료 장비 상세의 두 버튼은 미완료 장비와 달리 간격 적용 루프에 도달하기 전에 return했다. 완료 분기에도 8px 하단 간격을 적용했다. 이미 보유했거나 제작 중인 장비에 제작 목표 버튼을 primary로 강조하지 않는다.

RC3 최초 `equipment-navigation` 행동 검사는 117개, `inventory`는 524개를 통과했다. 위 후속 마감은 해당 이미지 검토 뒤 추가했으므로 최종 소스의 재검수가 별도로 필요하다. 검사 성공과 시각 검토의 시점을 혼동하지 않는다.

최종 이미지에서는 완료 장비 버튼 간격이 분리되었고, 보유 라이노의 제작 목표 버튼은 보조로, 비보유 헬리오스의 목표는 주요 행동으로 표시된다. `validation-final/inventory`의 추가 간격 검사 포함 530개와 `equipment-navigation`의 117개를 확인했다. `riven-capture`의 수동 취소/최소 크기 150%/8속성 비교 PNG도 열어 취소 범위 문구·비활성 상태·비교 행/등급/수치 정렬을 확인했으며 112개 행동 검사가 통과했다. 일정 대시보드와 340px/150% 오버레이, 주무기/보조무기 150%와 모드 프레임 확대도 열어 확인했다.

## 격리 메뉴 검수의 경계

실제 사용자 데스크톱의 포커스나 입력을 바꾸지 않는 `ShowActivated=false` 검수 창에서는 ContextMenu의 popup HWND가 키보드 초점과 native 메뉴 모드를 잡지 못했다. 진단값은 `Menu.Focus=false`, 논리 focus는 ContextMenu, 실제 Keyboard.FocusedElement는 호출 버튼이었다. 이를 제품의 방향키 결함 또는 방향키 전체 검증 성공으로 표현하지 않는다.

[공식 WPF ContextMenu](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/Controls/ContextMenu.cs), [MenuBase](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/Controls/Primitives/MenuBase.cs), [MenuItem](https://github.com/dotnet/wpf/blob/main/src/Microsoft.DotNet.Wpf/src/PresentationFramework/System/Windows/Controls/MenuItem.cs)의 기본 키/메뉴 모드를 확인했다. 제품에는 이를 대신하는 사용자 정의 방향키·Enter·Escape 동작을 추가하지 않는다.

검사는 실제 열린 메뉴의 UI Automation Invoke/ExpandCollapse로 파일·클립보드 명령 및 설정 변경을 계속 필수 확인한다. 키보드 초점이 허용되면 첫 항목 이동·Escape 초점 복귀·Enter 후 닫힘까지 assertion하고, 허용되지 않으면 Down routed handler/논리 focus만 확인한 뒤 `menuLimitations`에 실제 선택 이동·native 종료·물리 초점 복귀의 미검증을 기록한다. 마우스 capture도 실제 얻었을 때만 바깥클릭 handler의 닫힘을 검사하며, 얻지 못하면 미검증으로 남기고 검수 팝업만 close API로 정리한다. 사용자 화면을 활성화하거나 커서를 움직여 이 제약을 우회하지 않는다.

## 성유물 교정 상태의 마지막 정합성 수정

불확실 fixture를 카드 하나의 직접 대입에서 실제 `ApplyRecognition → RefreshAsync` 경로로 바꿨다. 그 결과 미확정 보상에서 '후보 확인'이 강조되고 '게임으로 돌아가기'의 강조가 해제되는 실제 상태를 확인했다. 이후 마지막 이름을 교정했는데도 페이지에 '보상 1개 이름 확인 필요'가 남는 제품 결함을 발견했다. 이 결함은 행 배치나 OCR 정확도의 문제가 아니며, 수동 선택이 카드 내용만 바꾸고 페이지 Notice를 갱신하지 않아서 발생했다.

수동 품목 확정·보상 추가·제거 경로에서 현재 유효한 품목과 남은 미확정을 집계하도록 수정했다. 모두 선택되면 '보상 n개 확인 완료', 미확정이 있으면 남은 수를 표시하고, 마지막 보상까지 제거하면 기본 대기로 돌아간다. 새 수동 보상은 품목 선택 전 완료로 표시하지 않는다. 타이핑이나 취소는 이 완료 전환을 호출하지 않으며, 기존 원문/확정 품목과 상태를 유지한다. 인식 시간 필드·OCR·가격 모델은 변경하지 않았다.

UIA Invoke는 dispatcher에 버튼 실행을 예약하므로, 테스트는 '이름 수정 Invoke → idle → 입력 → Escape'의 실제 순서를 기다리도록 정리했다. 마지막 교정·잘못된 입력/취소·선택 제거·0개 초기화는 별도 필수 assertion으로 유지한다. 이 마지막 수정 전 `validation-fixes/relics`는 89개를 통과했으며, 마지막 제품 상태 수정 뒤의 재실행은 이 기록과 구분한다.
