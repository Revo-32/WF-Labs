# 자동 감지·숨김 UI 자원 사용 코드 리뷰 · 2026-10-27

사용자 요청에 따라 OCR 엔진과 독립된 코드 경로를 검토했다. 이 문서는 코드에서 확인한 작업량과 수정 내용을 기록하며, CPU·메모리 절감 수치는 통합 측정 결과와 구분한다. 게임 입력·포커스 변경·실제 화면 캡처를 수행하지 않았다.

## 수정한 항목

### 전경 게임 판별

리벤 자동 감지는 대기 중 750ms마다, 카드가 보이면 400ms마다 `RelicCapture.GameWindow()`를 호출했다. 이 메서드는 Warframe 프로세스 두 이름을 열거하고 각 창 핸들을 확인한다. 게임이 없으면 매번 예외를 생성했다.

주기 감지에 `ForegroundGameWindow()`를 사용하도록 변경했다. 현재 전경 HWND의 소유 PID를 매번 네이티브로 확인하고, 같은 살아 있는 프로세스는 하나의 `Process` 핸들과 판별 결과를 재사용한다. PID 또는 HWND 재사용은 현재 소유 PID와 보존한 핸들의 `HasExited` 확인으로 처리한다. 전경 프로세스가 바뀌면 이전 핸들을 해제한다. 다른 앱이나 WF Labs 편집 창이 전경이면 캡처를 시작하지 않는다. 명시적인 게임 복귀 등에 필요한 기존 `GameWindow()`의 동작은 유지한다.

이 캐시는 일정 오버레이와 리벤 감지에서 공유하며 최대 한 프로세스만 보존한다. `ForegroundIdentityLookups`는 새 프로세스 조회 횟수이고 `ClearForegroundGameCache()`는 수명 종료·검수 정리에 사용한다.

`--relic-auto-check`는 전경을 바꾸지 않고 격리된 WF Labs HWND를 판별 helper에 전달한다. Warframe 거짓 양성 0, 반복 32회의 PID identity 재사용, 캐시 해제 뒤 새 조회, 잘못된·닫힌 HWND, 포커스 미변경을 확인한다. 실제 Warframe의 긍정 판정과 PID/HWND 재사용을 직접 실험한 것으로 확대하지 않으며 검사 결과의 범위에도 이를 명시한다. 통합 실행 결과는 별도 산출물을 따른다.

### 숨긴 일정 대시보드

일정 알림 또는 오버레이를 사용하면 일정 페이지를 떠난 뒤에도 1초 타이머가 필요하다. 기존에는 이때 메인 대시보드의 다음 S티어 탐색, 지역 상태, 툴팁·브러시 생성, 상점·인카논 표시 갱신도 매초 수행했다.

이제 메인 대시보드는 실제 표시 중일 때만 갱신한다. 페이지 이탈·숨김·최소화 중에는 자료 변경을 보류하고, 알림·만료 확인 및 게임 오버레이의 `TickFeatures()`는 계속 수행한다. 페이지 로드·다시 표시·창 복원 시 최신 자료로 즉시 갱신한다. 상태 변경 이벤트는 페이지 이탈과 Dispose에서 해제한다. `UseData()`의 중복 목록 재구성도 하나의 갱신 경로로 모았다.

`DashboardUpdateCount`와 검수용 `DashboardVisibilityOverride`를 사용해 숨김 중 메인 UI 재구성이 0회이고, 새 균열 알림은 한 번 발생하며, 복귀 시 즉시 갱신되는지를 기존 일정 검사에 추가했다.

### 보이지 않는 수동 오버레이 갱신

일정 오버레이가 켜져 있어도 게임이 전경이 아닐 때는 창 생성과 행 모델 재구성을 생략한다. 이미 만들어진 창은 숨긴다. 사용자 편집 중인 오버레이는 게임 밖에서도 스타일·타이머를 계속 갱신한다.

### 인벤토리 자동 탐색의 OCR 양보·분할 실행

`InventoryMemoryReader.ReadAsync`에 자동/수동 구분과 OCR 우선권 콜백을 추가했다. 자동 탐색은 128MiB 읽기 한도·250ms의 협력적 시간 예산과 1MiB 청크를 사용하고, 수동 탐색은 기존 6초·8GiB 및 4MiB 청크를 유지한다. 큰 후보 복구 중 바이트 예산이 끝나도 현재 후보 위치를 유지해 다음 호출에서 새 예산으로 이어간다. 이미 진행 중인 탐색도 다음 읽기·안정성 재검증 청크에서 OCR에 양보한다. 한 번 시작한 제한 크기 JSON 파싱은 완료될 수 있으므로 250ms를 엄격한 최대 지연이라고 표시하지 않는다.

영역 열거와 읽기 주소는 slice 사이 이어가며 검색 범위를 줄이지 않는다. 이전 호출의 원시 버퍼를 보존하는 대신 다음 호출이 직전 최대 2MiB를 재판독한다. 따라서 한 청크만 처리한 뒤 멈춰도 커서가 뒤로 돌아가지 않고, 경계에 걸친 JSON을 놓치지 않는다. 부분 읽기로 생긴 주소 공백은 연속한 바이트처럼 합치지 않는다.

PID와 프로세스 시작 시각으로 프로세스 교체를 확인하고, 종료·취소·Dispose 시 탐색 상태를 정리한다. 선택하지 않은 `Process` 객체도 Dispose한다. 버퍼는 성공·실패·양보·취소 모두 finally에서 Clear하고, 큰 후보를 검증하는 두 번째 사본은 최대 1MiB로 제한한다. 기존 12/32MiB 후보 복구 범위와 바이트 일치 검증은 유지한다.

`InventoryReadResult.Deferred`로 진행 중 양보를 정상적인 전체 검색 완료와 구분한다. 호출부의 자동 이어읽기 예약은 단일 타이머로 제한하고 성공·CompletePass·자동 끄기·Dispose에서 중단해야 한다. 이 연결과 통합 검수는 주 담당자·UI 담당자가 수행한다.

`InventoryMemoryChecks.cs`의 검사는 자기 프로세스에 할당한 3MiB 가짜 영역만 사용한다. 1MiB 경계에 걸친 JSON을 한 청크 뒤 양보하고 다음 slice에서 정확히 복구하며, 캐시 재검증·0바이트 선행 양보·취소 후 재시작·Dispose 이후 차단을 확인한다. 실제 게임 메모리를 읽는 검수와 구분한다.

## 유지한 동작과 추가 검토 후보

- `VerticalMarquee`는 실제 표시·내용 초과 시에만 30fps 렌더 변환을 사용하고, 숨김·Unload 시 애니메이션을 해제한다. 매 프레임 레이아웃 재구성은 하지 않는다.
- `OverlayPositioner`는 위치·크기가 같으면 `SetWindowPos`를 반복하지 않는다. 다른 앱의 오버레이 순서를 주기적으로 끌어올리지 않는 기존 보호도 유지한다.
- `RelicAutoDetector`는 증분 로그를 500ms마다 확인하며 한 번에 읽을 분량과 부분 줄 길이를 제한한다. 성유물·리벤에서 같은 로그를 두 번 확인하는 비용은 남아 있으나, 공유 tail 수명·구독 처리를 새로 만들기보다 측정 후 판단하는 편이 안전하다.
- 자동 탐색의 3초 이어읽기와 기존 30초 동기화 주기가 겹쳐 작업을 중복 생성하지 않는지, 2분 시세 갱신 빈도가 증가하지 않는지 통합 검수가 필요하다.
- 인벤토리 검색의 문자 입력마다 추천 목록 정렬·상세 재구성과 2분마다 저장 시세 전체 재파싱도 UI 반응성 측정 후보다. 이번 담당 범위에서는 이 파일을 변경하지 않았다.

## 통합 검증에 필요한 항목

- Release 빌드와 전체 Core 검사.
- `--riven-capture-check`: 자동 판별, 이전·이후 카드, 갱신·화면 이탈 동작.
- `--relic-auto-check`: 기존 자동 감지·로그 수명과 충돌 보호.
- `--schedule-check`: 숨김 중 알림 및 복귀 즉시 갱신을 포함한 실제 UI 이벤트.
- 대기·최소화·다른 탭·일정 오버레이·반복 OCR 구간별 CPU 시간, private bytes, working set, 핸들·스레드 추이 측정.

## 통합 후속 확인

2026-10-27의 후속 통합에서는 `artifacts/ocr-performance-20261027/validation-complete/validation-summary.json`의 18단계를 통과했다. 인벤토리 자기 프로세스 영역·이어읽기/중복 타이머는 530개 검사 안에 포함됐고, 리벤 자동 판독/비교·상태는 112개, 수동 교정과 실제 메뉴 명령을 포함한 최종 성유물은 95개 검사로 확인했다. 실제 게임 인벤토리 동기화 성공 검수로 확대하지 않는다.

전경 identity 검사의 첫 실패는 private 창의 Loaded에서 native `WS_VISIBLE`이 아직 false인 시점에 조회 횟수를 검사했기 때문이었다. ApplicationIdle 뒤 true가 되는 것을 `relic-auto-fixed/foreground-identity.json`에서 확인한 뒤 검사했으며, 실제 캡처의 가시성·최소화·PID guard는 유지했다.

4회 순차 CPU/RAM 비교는 `docs/OCR_PERFORMANCE_2026-10-27.md`와 `resource-comparison.json`을 따른다. 대기 CPU 감소나 큰 RAM 절감을 확인한 것으로 해석하지 않는다. 반복되는 동일 리벤 상태는 기존 equality guard가 UI·JSON 쓰기를 모두 생략하는 것도 읽기 전용으로 재확인했다.

코드 경로가 줄었다는 사실만으로 실제 CPU·RAM 감소율을 확정하지 않는다. 통합 빌드·동작 검사와 동일 조건의 측정은 주 담당자가 수행한다.
