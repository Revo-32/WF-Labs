# 검색·입력·상태 표시 검수 — 2026-10-24

## 원인과 수정

사용자가 제시한 모드 검색창의 커서가 안내 문구 중간에 보이는 현상에는 두 원인이 있었다.

1. 안내 문구의 표시 조건이 빈 문자열만 검사해, 검색창이 포커스를 받아도 문구가 남았다.
2. 공통 TextBox 템플릿의 Border와 `PART_ContentHost`에 전달된 Padding이 중복 적용돼 실제 커서와 안내 문구의 시작점이 달랐다.

공통 TextBox의 중복 여백을 제거했다. 근접/주무기/보조무기 보관함, 자료실, 엑실러스/근접/조우 아케인 선택창, 근접/총기 리벤 옵션 도감은 공통 `SearchField`를 사용한다. 리벤 옵션의 숫자 입력칸에도 포커스 상태를 고려한 안내 표시를 적용했다.

## 입력 흐름

| 상태·동작 | 표시와 결과 |
|---|---|
| 검색어 없이 다른 곳에 포커스 | 돋보기와 검색 범위 안내 |
| 검색창 포커스 | 안내 문구 즉시 숨김, 실제 입력 커서만 표시 |
| 검색어 입력 | 고정된 오른쪽 영역에 × 버튼 표시, 입력 영역 폭 유지 |
| 결과 없음 | 보관함에도 검색 결과 없음 표시 |
| × 실행 | 검색어 삭제 후 입력창 포커스 유지 |
| Tab | 입력한 검색어가 있으면 지우기 버튼으로 이동 가능 |
| 검색어가 있는 상태에서 Esc | 검색어만 삭제 |
| 아케인 선택창의 빈 검색창에서 Esc | 선택창 닫기 |
| 한국어 조합 중 Esc | 검색어 삭제/선택창 닫기가 조합을 가로채지 않음 |
| 무기 검색창 최초 클릭 | 기존 이름 전체 선택, 이후 클릭은 일반 커서 배치 |

검색 안내는 TextBox의 실제 값에 넣지 않는다. 무기 검색은 기존처럼 화살표 탐색과 명시적 확정을 분리하며, 입력 중인 후보를 자동으로 무기 선택이나 계산에 반영하지 않는다. 기존 Ideal/ClearType 글자 렌더링을 유지한다.

## 목적이 있는 모션

Microsoft의 [Windows 모션 지침](https://learn.microsoft.com/en-us/windows/apps/design/signature-experiences/motion)에서 상태 간 연결, 일관된 반응, 문맥에 맞는 짧은 모션을 참고했다. 입력 안내의 구현에서는 [WPF TextBox 안내 문구 문서](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/controls/how-to-add-a-watermark-to-a-textbox)를 참고했다. 외부 코드를 복사하지 않고 기존 WPF 컴포넌트에 맞춰 작성했다.

- 일반 드롭다운과 무기 검색의 화살표가 열림/닫힘에 따라 140ms 동안 회전한다. 빠르게 재조작하면 현재 각도에서 마지막 상태로 이어진다.
- 검색어가 처음 생길 때 지우기 아이콘만 100ms 동안 나타난다. 검색어가 있는 동안 매 글자마다 반복하지 않는다.
- 안내 문구 숨김, 검색 결과 필터링, 입력 커서, 글자 크기/위치에는 모션을 적용하지 않는다. 안내를 서서히 숨기면 커서와 겹치는 중간 상태가 다시 생기므로 즉시 숨긴다.
- 경량 모드와 Windows의 클라이언트 영역 애니메이션 설정을 따른다. 경량 모드로 전환하면 이 모션들의 진행 중인 애니메이션도 종료한다. 상시 타이머나 렌더링 루프를 추가하지 않는다.

## 검수 범위

`--search-interaction-check`는 실제 WPF 창의 UIA Focus/Value/Invoke/ExpandCollapse, Tab 탐색, 키/조합 이벤트를 사용한다. 검색창 10개 경로 × 다크/라이트, 리벤 수치 입력 24개, 글꼴 3종 × 테마 2종 × 100/125/150% 시각 트리 DPI, 지우기/포커스/IME/Esc/모션 상태를 검사한다. TextComposition 이벤트 검사이며 실제 Windows IME 후보창을 조작하는 시험과는 구분한다.

일반 잘림 검사에 더해 실제 커서 시작점, 텍스트 뷰포트와 지우기 버튼 경계, 버튼 출현 전후의 입력 폭도 검사한다. 검색 입력 검사를 `tools/validate.ps1`에 연결했다. 계산 회귀, 장착/팝업 조작, 전체 배치·테마·스크롤·UI smoke도 실행한다. 최종 수치와 파일 해시는 `artifacts/search-motion-verification.json`에 기록한다.

수정된 검색창·아케인 선택창·리벤 입력 화면 이미지를 직접 확인했다. 스크린샷 렌더링 수와 실제 입력 동작 검사 수를 구분한다. 전체 UI smoke의 추가 `drag-geometry.json`은 합격 여부 필드가 없는 좌표 기록이다. 검증에 사용한 Desktop/Core 및 변경 소스의 SHA-256은 위 JSON에 기록했다. 실행 앱과 계산 테스트가 사용하는 Core DLL 해시도 일치한다.

개발 실행 파일: `src/TennoForge.Desktop/bin/Release/net8.0-windows/WFLabs.exe`. 이번 작업에서는 설치 파일이나 공개 업데이트를 만들지 않았다.
